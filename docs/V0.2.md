# agentspeedrun v0.2 target

From a sequential six-auditor review of cdf98f1 plus an adversarial critic; every finding with evidence, scenario, fix and verdict is in [audit/v0.1.0.json](audit/v0.1.0.json).

## 1. Theme

v0.2 is the "numbers you can trust on your own machine" release. v0.1 records runs, but several things make its results wrong or dropped without any sign:
- the clock (pause and turn accounting),
- the daemon and client plumbing (401s and dropped prompts, zombie daemons, empty logs, hooks that block Claude Code),
- the verifiers (any old commit counts as "evidence_verified").

v0.2 fixes those. It also makes four structural changes that every later feature depends on, and they get costlier with each release that keeps the v0.1 format:
- hash over the stored bytes,
- verification rules versioned together with categories,
- prompt text moved out of the hash chain,
- device signatures, so a log is attributable to a key and not only to a machine (W9).

Sync, leaderboards and server anchoring are out of scope. v0.2 only has to make sure nothing blocks them. The docs stop claiming tamper-proofing that a local-only design cannot give.

## 3. v0.2 scope

### W1. Integrity foundations (do first; every other workstream depends on it)

**Deliverables**

- Hash and verify the stored JSON body: parse it as a `Value`, remove `hash`, canonicalize, then hash. The typed parse is used only for folding (A2-5, C-3).
- A rule plus a lint/test that every additive payload field has `#[serde(default, skip_serializing_if = ...)]`.
- `fold` and `live` skip rows they cannot parse and report them, instead of returning 500 for the whole request.
- `migrate()` refuses to run when `user_version > MIGRATIONS.len()`, and runs `VACUUM INTO` as a backup before applying migrations (A5-4).
- **SCHEMA_VERSION bump to 2**, bundling:
  - (a) PromptSubmitted v2: `content_digest = HMAC-SHA256(prompt key, redacted text)` (hex) plus `length` (characters) and the redacted flag. The prompt key is 32 random bytes, hex, in `$SPEEDRUN_HOME/prompt.key` (0600). It is separate from the signing key, so a key rotation leaves earlier digests checkable, and it never leaves the machine (D7). The text moves to a `prompts` table (`event_id`, `content`), outside the chain and deletable (A6-7).
  - (b) Predefined milestone ids in new runs are namespaced `<category>@<version>/<key>` (A6-8). The API still accepts a predefined milestone's category key in place of its id, and the log stores the full id.
  - (c) `Event` gains `sig` (ed25519 over `hash`, outside the canonical body), and `RunStarted` gains the P0 ownership fields: `device_pubkey`, `start_head`, `start_head_committed_at`, `ruleset_digest`, `disclosure_commitment` (W9). Signing joins the same bump so a v0.2 archive is already publishable.
- Nothing reads v1 events, bare milestone ids or unsigned events (D4): the v2 format is the only one.

The v2 prompt digest in (a) is deliberately opaque. `disclosure_commitment` uses a
separate revealable per-run key, so commit-then-reveal does not need a second
bump later.

**Acceptance**

- A frozen v0.2 fixture DB is checked into the repo. `speedrun verify` passes on it after a dummy optional field is added (CI test).
- One corrupt row yields a 200 from `/v1/live` with an error entry.
- A binary opening a DB whose schema is newer than its own exits non-zero with a clear log line.
- A v2 run whose prompt text has been deleted still verifies.

### W2. Verification correctness and versioned rules

**Deliverables**

- Evidence requirements move from `required_kind` into the category JSON (`requires: {...}, rule: "<name>@<n>"`).
- They are copied into `MilestoneProposed` as an additive field.
- `Job` carries `(category_id, version, key)`, and verifiers dispatch on it.
- `MilestoneVerified` gains additive `rule_version` and `observed` fields (Stripe `{paid_at, amount, currency, object_id, livemode}`, CI `{completed_at, head_sha, workflow_path}`, URL `{fetched_at, final_url, status}`) (A6-2, A6-4).
- `RunStarted` records the HEAD sha and its committer time (additive).
- Category rules, fixed in place (D4 retires the published @1 rules; versioning applies to changes after v0.2):
  - **any-percent / hundred-percent:** a commit must not be an ancestor of the start HEAD. A demo milestone needs a url or ci_run (A3-1).
  - **first-revenue:**
    - Stripe checks: `Stripe-Version` is pinned. An invoice or session must resolve to a real charge, failing closed. `paid_out_of_band` and `amount_paid==0` are rejected. A refund above a small threshold counts as refunded. Emails are normalized and a missing customer email is rejected (A3-2, A3-3).
    - Legal pages: at least two distinct URLs on the deployed site's registrable domain. Text inside `a`/`nav`/`footer` is ignored when classifying (A3-4).
    - first-payment has an `after:` dependency on deployed and legal-pages, and its split is dated at `paid_at` clamped to [start, claim] (A6-3 ordering, A6-4).
- `finish_verification` rejects a job whose `cause_event_id` is no longer the milestone's current claim, and never dates a verification before the latest invalidation (A2-2).
- Lower bound on `occurred_at`: no earlier than the run's last event minus skew, unless the event is a spool replay, which `speedrun flush` marks with the `X-Speedrun-Replay: 1` header. A replay may still not predate its run. The verified-claim grace period is cut to the actual check time (A2-6).

**Acceptance**

- Mocked-verifier tests for every scenario in A3-1/2/3/4 and A2-2 fail closed under the current rules.
- A backdated claim gets 400.

### W3. Clock and turn accounting

**Deliverables**

- Hook `StopFailure`. On a second `AgentTurnStarted` in a session with a turn already open, close the old turn at the last activity seen for that session, capped at a maximum turn length (A2-3).
- Stale-turn rule: an open turn with no activity for N minutes ends at its last activity.
- Pair turn starts and ends by `occurred_at`, and ignore an end that is earlier than the open start (A2-4).
- A cheap, debounced activity hook (PostToolUse) reopens a turn after a blocked Stop (A4-4).
- Spool: use flock instead of rename plus mtime, and prepend when re-spooling (A2-4).
- Classify non-human UserPromptSubmit input (subagent reports, /loop, cross-session messages) where it can be detected. Such input is stored with `source` and never starts a run (A4-3).
- pi records prompts from `input` events with `source` interactive or rpc (A4-6).
- Cache the Claude Code model from SessionStart per session (A4-8).

**Acceptance**

These scratch-fold tests from the audit become permanent regression tests:
- start@0, start@60 in one session gives agent time well under 60 min,
- start@0, start@60, end@30, end@80 gives 50 min,
- a paused run with agent work gives non-zero agent_ms.

### W4. Daemon, upgrade and operations

**Deliverables**

- The address is tied to the data dir: the daemon writes its chosen port to `$DATA_DIR/addr` (0600), and clients read it. The fixed 7477 remains only as a fallback, and the choice between a port file and a socket is decision D3 (A5-3, A1-1).
- `/v1/health` returns `protocol_version`, the binary version and a data-dir fingerprint. It stops sending the token on health, and the client checks HMAC(token, nonce) before sending a body (A1-1).
- When the daemon is older than the CLI, `ready()` sends an authenticated `POST /v1/shutdown` and starts the new daemon (A5-4).
- `speedrun daemon stop|restart|status` waits for the PID to exit, and install.sh calls it (A5-1, A5-4).
- `speedrun doctor` prints the log tail, both versions, the token/data-dir match, spool and rejected counts, and the adapter version stamps (A5-2, A4-9).
- `speedrun backup <file>` uses `VACUUM INTO`. Checkpoint the WAL on shutdown and periodically. Regenerate device_id on import (A5-5).
- Accept only the display token in `?token=` (A1-7).
- Free-text fields are stripped of control characters on ingest and escaped on render (A1-4).

**Contract** (fixed by the leader for the Wave 3a tests; M2, M4, M7.c, M8 and W4 build to it)

- *Start order.* The daemon takes an exclusive lock on `$DATA_DIR/speedrund.lock`, binds its listener, then creates `token` and `display-token` atomically (write a temp file, then link it to the final name; an existing token is read, never replaced), then opens and migrates the database. A daemon that cannot lock or bind exits non-zero having written no token and no database.
- *Address (D3).* The daemon listens on `SPEEDRUN_ADDR` if set, else on 127.0.0.1:7477, or on a free loopback port when 7477 is taken. After binding it writes the bound `host:port` to `$DATA_DIR/addr` (0600, replaced atomically). Clients use `SPEEDRUN_ADDR`, else `$DATA_DIR/addr`, else 127.0.0.1:7477.
- *Health.* `GET /v1/health?nonce=<hex>` returns `HealthResponse`: `protocol_version` (`api::PROTOCOL_VERSION`), `data_dir_id` (hex SHA-256 of the canonical data-dir path) and `proof = digest::token_proof(token, nonce)`. It never carries a token. Before sending a body, the client asks with a fresh random nonce; a missing or wrong proof means a daemon for another data dir, so the write is spooled and nothing is sent.
- *Spooling.* On 401 the client re-reads the token and retries once, then spools. 5xx and timeouts spool. Other 4xx are reported as before.
- *Hook budget (M8).* The fresh event is sent first, with no flush before it. The spool is then flushed for at most 3 s of wall clock; entries not reached stay spooled.
- *Doctor.* `speedrun doctor` exits 0 whether or not a daemon answers, and prints one item per line: `cli: <version>`; `daemon: <version> (protocol <n>)`, `daemon: not reachable at <addr>` or `daemon: answers for another data directory (<addr>)`; `data dir: <path>`; `spooled: <n>` (lines in the pending and flushing spool files); `rejected: <n>` (lines in `rejected.jsonl`); `spool write failures: <n>`; then the tail of `speedrund.log`.
- *Write failures (M7.c).* Every failed write to the spool or `rejected.jsonl` adds one to the decimal count in `$DATA_DIR/spool-write-failures`.

**Contract for stopping and restarting** (Wave 3b; W4.b builds to it)

- *Pid.* `HealthResponse.pid` is the daemon's process id. A pid has exited when `kill -0 <pid>` fails; liveness is checked with the `kill` binary, never `ps` (setuid, so the check sandbox cannot run it).
- *Shutdown.* `POST /v1/shutdown` takes the full token only (the agent and display tokens get 401). It answers 202 with an empty body and then stops the daemon as SIGTERM does: open live streams end and the process exits within about 2 s.
- *`speedrun daemon status`* prints `daemon: <version> (protocol <n>) pid <pid> at <addr>` and exits 0 when a daemon proves this data dir's token; otherwise it prints the matching `doctor` daemon line and exits 1.
- *`speedrun daemon stop`* asks health (with a nonce) for the pid, sends `POST /v1/shutdown`, and returns only once that pid has exited, polling for up to 5 s; it then exits 0. A pid still alive after 5 s exits 1. With no daemon answering it prints `daemon: not running` and exits 0. A daemon that answers for another data directory gets no token and no shutdown: `stop` prints doctor's `daemon: answers for another data directory (<addr>)` line and exits 1.
- *`speedrun daemon restart`* is `stop`, then starts speedrund even when `SPEEDRUN_NO_AUTOSTART` is set, waits up to 10 s until the new daemon proves the token, and prints the `daemon status` line for it; if no daemon proves the token by then, it prints doctor's daemon line and exits 1. If its stop half fails (a daemon for another data directory, or the pid still alive after 5 s), it reports that, exits 1 and starts no second daemon; if speedrund cannot be spawned, it exits 1 at once with doctor's daemon line. `stop` reports a failed `POST /v1/shutdown` and exits 1 rather than assume the daemon exited. Failures exit through `main`'s ordinary exit path. With a live stream open, exactly one daemon is left: the old pid has exited and health answers with the new one.
- *Decision.* `ready()` does not stop an older daemon on its own in this wave; install.sh will call `speedrun daemon restart`. An automatic restart from a hook could interrupt a run the user is watching, and the explicit command gives the same outcome on upgrade.

**Acceptance**

- Two daemons started concurrently 50 times give 0 token mismatches.
- A hook run with a mismatched data dir spools and `doctor` explains why.
- An upgrade with an SSE client open leaves exactly one daemon alive.
- `GET /v1/live?token=<full>` returns 401.

### W6. Trust and consent

**Deliverables**

- Separate provenance (claimant user|agent, derived from the token) from trust strength. MCP and tools get a separate agent token, and the daemon ignores client-supplied trust (A3-5).
- Predefined self_declared milestones claimed by the agent stay pending until the user confirms them.
- Per-user opt-in for a committed `.speedrun/project.json`, through a local allowlist keyed by project_id and root. The ancestor walk stops at the git toplevel and never goes above $HOME (A1-8).
- `MilestoneProposed` gains additive `derived_from` and `slug` fields (A6-5).

**Contract for the allowlist** (Wave 3a)

- `$DATA_DIR/trusted-projects.json` is a JSON array of `{ "project_id", "root" }`, `root` being the canonical project root. Hooks, `ingest`, the MCP server and tools record only for a project listed with its root; otherwise they exit 0 and record and spool nothing.
- `speedrun init` adds the project it creates. `speedrun init --trust` adds the project whose `project.json` is found from the working directory, without changing that file and without the daemon.
- The project search walks up from the working directory, stops after the git toplevel (the first directory holding `.git`), and never looks above `$HOME`.

**Contract for provenance and confirmation** (Wave 3b; W6.a builds to it)

- *Agent token.* At start the daemon creates `$DATA_DIR/agent-token` as it creates `token` (temp file then link; an existing file is read, never replaced). It is accepted only in the `Authorization` header, and only on `POST /v1/events`, `POST /v1/projects/{id}/events`, `GET /v1/projects/{id}/active-run`, `GET /v1/runs/{id}`, `GET /v1/runs/{id}/events` and `GET /v1/categories`. Every other authenticated route answers it 401; `/v1/health` reads no token and answers it as it answers anyone.
- *What the agent may send.* Through the agent token the daemon accepts only `milestone_proposed`, `milestone_reached`, `milestone_invalidated`, `agent_turn_started` and `agent_turn_ended`. Any other payload is 403 and nothing is appended.
- *Claimant and trust.* The daemon sets `claimant` on every `milestone_reached` from the token it arrived with (full token `user`, agent token `agent`), overwriting what the client sent, and derives the claim's trust from it: `user` gives `self_declared`, `agent` gives `agent_claimed`. A claim sent as `evidence_verified` is still 400; evidence raises trust only through verification.
- *Confirmation (D6).* A milestone whose `required_trust` is `self_declared` and whose current claim has claimant `agent` is `pending_confirmation` and does not count, whatever verification adds. `milestone_confirmed { milestone_id }` (full token only; a category key names the milestone as in other milestone events) clears it, and the milestone counts from the confirmation's time. It is 409, like other events the run's rules refuse, unless the milestone is pending. A claim with claimant `user` counts at once and is never pending. An agent claim on a milestone that already counts, by the user's claim or confirmation, leaves it counting with its split unchanged. An invalidation clears pending, and a later agent claim makes it pending again.
- *Clients.* The MCP server and `speedrun tool` send with the agent token; hooks, `ingest` and the other commands send with the full token. `speedrun confirm <milestone>` sends `milestone_confirmed` for the active run. A spool entry records `"credential": "agent"` when it was written for the agent token, and `flush` replays it with that token. Health proofs still cover the full token. A missing `agent-token` is treated as a missing `token` is: the request counts as unreachable and is spooled. A full-token spool entry omits `credential`.
- *Scope.* This records provenance; it is not a boundary against an agent that runs `speedrun` commands as the user.

**Acceptance**

- A claim from the agent token on a `self_declared` category milestone (any% `scaffold-runs`) does not count until the user confirms it. (No category has a `tax-compliance` milestone; the item names the rule, not that milestone.)
- Cloning a repo that has project.json records nothing until the user runs `speedrun init --trust`.

### W7. Product: PBs and the live contract

**Deliverables**

- PBs scoped to the project by default (A6-6).
- `category_version` pinned in project.json at init, with `speedrun init --upgrade-category` to move.
- `comparable_with` metadata on category versions.
- LiveSnapshot gains `protocol: 1` and `source {kind, id}`, the cursor is defined as comparable only within one source, and LiveMilestone gains `counted_at`, description and an evidence summary. Recently abandoned runs are either emitted or removed from the docs (A6-9).

**Contract for pinned categories and the snapshot** (Wave 3b; W7.b builds to it)

- *Pin.* `speedrun init` writes `category_version`, the latest built-in version of the category, into `project.json`. `speedrun init --upgrade-category` rewrites only `category_version` of the `project.json` found from the working directory, to the latest built-in version, keeping `project_id`, `category_id` and `created_at`, and prints `<category> <old> -> <new>` (`unpinned` for a file without the field).
- *Prompts.* Hooks and `ingest` send the pinned version as `PromptRequest.category_version`. A run started by that prompt uses exactly that `(category_id, version)`; a pair the daemon does not know is 400 and starts no run. Without the field the daemon takes its latest version.
- *Snapshot.* `LiveSnapshot.protocol` is `live::LIVE_PROTOCOL_VERSION` (1) and `source` is `{ "kind": "local", "id": <the daemon's data_dir_id> }`. A cursor is comparable only with cursors from the same source.

**Acceptance**

- The PB shown comes from the same project.
- Upgrading the binary does not change a project's category version.
- The snapshot JSON schema has a `protocol` field.

### W9. Commons foundations: device signing and disclosure commitments

From [`COMMONS.md`](COMMONS.md) §3–§5. Nothing here leaves the machine, so it
ships in v0.2; it is the local half of the publishing pipeline. Do it together
with W1, because both change the one v2 bump.

**Deliverables**

- On first start the daemon generates an ed25519 keypair at
  `$SPEEDRUN_HOME/device.key` (0600) and uses its fingerprint as `device_id`.
  `SPEEDRUN_DEVICE_KEY` overrides the path. A missing or unreadable key is a
  hard error, never a silent regeneration.
- Every event gains `sig`: ed25519 over the `hash` bytes, excluded from the
  canonical body exactly like `hash`. `speedrun verify` checks signatures and
  fails an event without one (D4: there are no v1 logs to accept).
- `RunStarted` gains `device_pubkey`, `start_head`, `start_head_committed_at`,
  `ruleset_digest` and `disclosure_commitment`, all additive with
  `skip_serializing_if`.
- A run's chains are keyed by `(run_id, device_id)`. `device_id` is the
  fingerprint of the device's first key and does not change on rotation.
  A chain's first event names its key: `RunStarted.device_pubkey` for the
  device that started the run, `DeviceJoined.device_pubkey` for any other.
  `verify_chain`, `verify_event_signatures` and `fold` take a run's events
  with each chain in seq order and the chains in any order; `fold`
  interleaves the chains by `occurred_at`. One device behaves exactly as
  today. The store keeps one chain per run until import exists (P1).
- Each run generates a disclosure key at start: 32 random bytes, hex, in
  `$SPEEDRUN_HOME/disclosure/<run_id>` (0600). `RunStarted` stores only the
  sha256 of its bytes. `speedrun export --tier 2` (`GET
  /v1/runs/{run_id}/export?tier=2`) writes, per prompt,
  `commitment = HMAC-SHA256(disclosure key, redacted text)` with length and
  redacted flag, and no prompt text.
- `speedrun key rotate` (`POST /v1/device/rotate`) replaces the device key.
  In one transaction, the daemon appends `DeviceRotated { new_pubkey,
  certificate }`, signed by the new key, to every chain of this device that
  names the old key, where `certificate` is the old key's ed25519 signature over
  `agentspeedrun-rotation:` followed by the new hex public key. Earlier events
  keep verifying, from public keys alone, however many rotations a run sat
  through without writing. The old key is not kept. The new key waits in
  `<key file>.next` until the transaction commits; the next start finishes a
  rotation that committed and discards one that did not.
- `ruleset_digest` is the sha256 of the canonical JSON of the category the run
  pinned, as `/v1/categories` serves it, so a published run names its rules
  even after `categories/` changes.
- `start_head` and `start_head_committed_at` are the project's git HEAD and its
  committer time when the run started, when the project root is a repository.

**Acceptance**

- A log edited and re-hashed fails `speedrun verify` with a signature error.
- Two device keys append to one run and `speedrun status` folds both without an
  ordering error.
- `speedrun export --tier 2` for a known prompt yields a commitment a test

## 4. Explicitly not in v0.2

- **Server anchoring, sync, leaderboards (A3-7, A6-8 multi-device model, A6-4 server-side Stripe check).** These need a backend and owner decisions. v0.2 only removes the format blockers (W1, W9) and fixes the docs. Without anchoring, local results are self-attested, so no leaderboard should exist yet.
- **Proof that a deployed site is controlled by the runner, and the CI provenance requirements (A3-6).** Exploiting the gap takes deliberate self-cheating, and there is no leaderboard in v0.2.
- **Stripe account-level checks for payments-live and tax (A6-3 beyond ordering).** The field names were not checked against the Stripe API, so these milestones stay self_declared, with the dependency ordering only.
- **Tying the Stripe payment to the project and re-checking refunds after completion (A3-3 remainder).** This needs a revocation event design. Revisit with sync.
- **Full SSRF hardening (A1-5).** The agent can already make network requests itself. Only a generic error message for connect and TLS failures goes in, as part of W2.
- **Windows support (A5-7).** Documented as unsupported.
- **A published TS/Swift live-display package (A6-9 remainder).** Wait until the protocol v1 has settled.
- **Anything that leaves the machine** — publish, accounts, boards, disputes, the transparency log (`COMMONS.md` P1–P4). W9 adds signing and commitments locally so the format is ready; the pipeline is not built.

## 5. Owner decisions

Made by the owner on 2026-11-01.

- **D1. License and public repo.** Public, licensed `MIT OR Apache-2.0`. W8 attestations, M1 pinning and issue intake are designed for outside users.
- **D2. Ranking clock.** `timed_ms` ranks runs and keys PBs, as `LIVE_DISPLAY.md` already states. Wall time stays beside it, so pause time is visible as its own number. There is no pause cap: the harness does not judge what pause time means (ideation while paused varies), and the community can form its own view.
- **D3. Transport.** The port file in the data dir (`$DATA_DIR/addr`, 0600) with the HMAC(token, nonce) health check; 7477 remains only as a fallback. Clients authenticate by the data-dir token, not by socket peer UID, because Zed's wasm runtime and VS Code may not reach a Unix socket.
- **D4. v0.1 history.** There is no v0.1 data to preserve, so v0.1 formats are retired, not supported: runs are re-folded under the M5 rule with no labels; nothing reads v1 events, bare milestone ids or unsigned events; the published @1 category rules are fixed in place rather than kept beside an @2. Versioning (events and categories) applies to changes made after v0.2.
- **D5. Multi-device model.** Decided by `COMMONS.md` C1: the person owns runs, devices are revocable keys, and chains are kept per (run, device), as W9 builds them.
- **D6. Agent trust default.** Agent claims on self_declared milestones always need the user's confirmation; there is no per-project setting.
- **D7. Prompt-text policy for PromptSubmitted v2.** The HMAC key is per device and never leaves the machine. Public proof about prompts comes from W9's per-run disclosure key.
