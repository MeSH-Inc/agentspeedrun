# Long-history and live-stream follow-up

Measured locally on 2026-11-02 after the turn-index and shared-live changes at `5646572`. The earlier [baseline](history.md) used the same machine and 30-sample closed-loop matrix. Raw output, including per-process `/usr/bin/time -l` statistics, is in [matrix.txt](after-2026-11-02/matrix.txt), [baseline-memory.txt](after-2026-11-02/baseline-memory.txt), and [open-loop.txt](after-2026-11-02/open-loop.txt). These are single local runs, not confidence intervals; the machine was checked for competing Rust builds before the timed sequence, but was not isolated from all background activity.

The original workload and timing boundaries are unchanged: a fresh signed single-project history, 30 loads and folds, then 30 sequential GET, append and wait-for-every-subscriber cycles. The release test executable runs directly under `/usr/bin/time -l`, so peak RSS includes fixture construction, verification, setup and teardown, not just the timed phase. The baseline did not originally record memory. For a new comparison, the original executable named in its raw log was copied before rebuilding (SHA-256 `b739bdee7b8ac763b0fdcedef16b32dd9ef6f0ced0e30b2c66243023f035019b`), then rerun separately on selected cases. Its identity rests on the preserved executable path and timestamp; the binary was not independently reproducibly rebuilt. The refactors are measured together, so differences cannot be assigned to either in isolation.

## Multiple projects and overlapping writes

The separate open-loop driver seeds three active projects, each with the indicated number of signed events, and starts five live subscribers. It schedules fixed-rate writes without waiting for prior responses. At most 16 requests may be in flight; excess offers are counted as client admission drops, not server failures. Scheduling-to-response and scheduling-to-last-subscriber include scheduler delay. Each subscriber's first observed cursor at or beyond a write counts as observing it; a later cursor counts as coalescing that subscriber-revision pair. After writes drain, the test waits for every subscriber to catch up to the final global cursor, verifies every run's signed chain, and checks event counts and unique IDs. The only events generated in this fixture are prompts, so no completion events alter the expected count. The 120-second request and catch-up deadlines bound failure waits. RSS is a whole-process peak as above.

The 500/s run offered work for 0.601 s and drained for another 0.036 s, completing 463.3 writes/s including drain. The 180/s and 20/s runs completed during their 1.668 s and 5.001 s offering periods. These short bounded tests expose overlap and overload but do not establish steady-state capacity, stalled-client behavior, or long-term queue stability.

## Memory

Peak RSS is the maximum resident size of each entire test process, reported in MiB (1 MiB = 1,048,576 bytes). Repeats are separate processes. The baseline executable was rerun for memory only; its original published timing figures are unchanged. Raw repeats are in [repeat-memory.txt](after-2026-11-02/repeat-memory.txt).

| Initial events | Subscribers | Baseline peak RSS MiB | After peak RSS MiB |
|---:|---:|---:|---:|
| 1,000 | 1 | 23.70 | 23.86 |
| 1,000 | 20 | 27.81 | 25.61 |
| 100,000 | 1 | 859.19, 986.16 | 1046.61, 1586.14 |
| 100,000 | 20 | 1170.61 | 1391.84, 1074.72 |

The first 100k/1 comparison rose by 187.42 MiB (21.8%), while the second after run was much higher. The 100k/20 after runs straddle the single baseline result. Both baseline /1 runs are below both after /1 runs, but the large variation, lack of repeated /20 baseline measurements, and inclusion of setup and allocator retention prevent attributing the increase or establishing a stable magnitude. A memory regression remains plausible and needs profiling; these numbers do not establish that the refactors are memory-neutral.

A separate untimed [logical-storage calculation](after-2026-11-02/index-storage.txt) counts 33,332 turn starts in the 100k fixture. On this build the turn index's coordinate and tree vector *elements* occupy 2,399,904 bytes: 24 bytes per coordinate and four 12-byte nodes per start. This excludes vector spare capacity, B-tree nodes, strings, turn-position maps, allocators and all other projections. It is a partial structural count, not a measurement of the refactor's total allocation or resident-memory impact.

Separate 100k/20 profiling runs captured three seconds each with macOS `sample` and 1-second `ps` RSS observations: [baseline sample](after-2026-11-02/profile-baseline-sample.txt), [after sample](after-2026-11-02/profile-after-sample.txt), [baseline RSS](after-2026-11-02/profile-baseline-rss.txt), and [after RSS](after-2026-11-02/profile-after-rss.txt). These runs used 8 and 20 cycles respectively, began sampling four seconds after launch, and did not run as part of the matrix. Rust frames in both release binaries are stripped to addresses, so the captures cannot attribute CPU time to a specific function. RSS fluctuated over each process lifetime; the RSS columns in those `ps` files are KiB. The one-second samples can miss true peaks and are not phase-attributed. The [run outputs](after-2026-11-02/profile-baseline-run.txt) and [after output](after-2026-11-02/profile-after-run.txt) record their separate workload measurements.

## Decision and recommended follow-up

Do not introduce a persistent projection cache on this evidence. Shared stream production and the turn index improve long-history latency substantially, but repeated full-history read/deserialization remains costly, the 3×100k burst queues for seconds, and the memory impact is unresolved. Next, profile allocations and live resident memory by phase with symbols in repeated before/after runs, including one and many subscribers, and set an explicit per-run and process memory budget. Then prototype a bounded in-memory per-run read model or snapshot reuse keyed by log head and source generation, with verification state and time-dependent values overlaid separately. Differentially check every update, retry, reordering and recovery path against full replay; measure eviction, rebuild, multi-project fairness, stalled subscribers and sustained open-loop pressure before deciding whether that prototype is worthwhile. Keep the event log authoritative and defer persistent derived state until its recovery, invalidation and operational cost have a measured justification.

Reproduce the matrix with `BENCH_EVENTS=1000,10000,100000` and `BENCH_SUBSCRIBERS=1,5,20` as separate invocations:

```sh
BENCH_EVENTS=10000 BENCH_SUBSCRIBERS=5 BENCH_ITERATIONS=30 \
  cargo test --release -p speedrund history_pressure -- --ignored --nocapture
BENCH_EVENTS=1000 BENCH_PROJECTS=3 BENCH_SUBSCRIBERS=5 \
  BENCH_RATE=180 BENCH_ITERATIONS=300 BENCH_MAX_INFLIGHT=16 \
  cargo test --release -p speedrund open_loop_pressure -- --ignored --nocapture
cargo test --release -p speedrund index_logical_storage -- --ignored --nocapture
```

For per-process RSS, build the test binary first and run that executable directly with `/usr/bin/time -l`, as in the raw logs. Measuring `cargo test` itself would include the build driver and is not the same process measurement.
